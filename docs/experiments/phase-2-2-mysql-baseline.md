## 单变量实验与决策

- **索引假设**：库存条件更新或订单查询可能扫描过多行。隔离库 `EXPLAIN UPDATE inventory ... WHERE ticket_type_id=1 AND available_stock>0` 使用 `uq_inventory_ticket`，估算 1 行；有效订单 `COUNT` 使用 `uq_active_order` 的 `(user_id,activity_id)` 前缀，估算 1 行；锁定读以全部三列使用 `uq_active_order`，类型 `const`。这是该库当前数据分布下的优化器估算，不是所有规模的承诺。未新增索引；订单插入维护主键、有效订单唯一键和两个外键索引，未单独测量其写入开销。
- **事务范围假设**：长事务可能放大竞争。入口是公开 `PurchaseService.purchase` 上的 `@Transactional`；活动/票种/重复订单查询、条件更新、订单插入均在内，未发现外部网络调用。将这些校验移到事务外可能改变并发语义，本轮未修改。`performance_schema.events_transactions_history` 某次全局快照 62 条有计时事务，平均约 1.704 ms、最大 2.453 ms；并非按请求或按轮归因，不能代表整轮分布。
- **连接池假设**：改变连接数可能降低等待。仅改变 `maximumPoolSize=5/20`，其余同 B0，在 100 iterations/s 对三种负载各运行三次。未测试 40。采样没有观察到连接池排队，两个候选的成功 TPS 无稳定改善，短时 P95 波动与 B0/B1 范围交叠；不接受候选，保留默认 10。

## 正确性与采样

每轮查询库存、有效订单数、重复有效订单、库存差额；将每条 201 返回的订单 ID 与数据库持久化 ID 比对。所有测量轮正确性均通过，无负库存、库存超过总量、重复有效订单或差额；所有成功 ID 都能查到。额外在隔离库运行 `PurchaseDatabaseIT#orderInsertFailureRollsBackStock`，插入失败回滚库存通过；这项故障注入是额外测试，**没有在每轮负载中执行**。测试后 `SHOW CREATE TABLE` 确认库存 CHECK 和有效订单唯一索引、状态 CHECK 存在；不是每轮单独检查 DDL。

Hikari 活跃/空闲/等待使用约 0.5 秒间隔的 Actuator 快照，不代表瞬时峰值；获取耗时是每轮前后计数差计算的平均值，不是 P95。每轮约一次用 root 只读采样 `performance_schema.data_lock_waits` 以及 MySQL CPU/内存，应用账号没有额外监控权限。所有锁等待瞬时采样为 0；全局 `Innodb_row_lock_waits` 每轮增量如表，属于整个实例，也包括监控或其他连接，不能完全归因到本次请求。零采样不证明没有锁等待。MySQL 死锁计数按本机 `SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks'` 未返回可用项，且正式 API 将未预期数据库异常统一映射为 `INTERNAL_ERROR`，因此无法从本次 HTTP 计数独立区分死锁与其他系统错误；实际观测到的 HTTP 500 为零，不等价于已测得死锁为零。

B0 负载期间 MySQL 容器单次采样 CPU 1.29%–23.00%、内存 564.1–569.5 MiB；B1 CPU 1.54%–31.70%、内存 576.0–582.8 MiB。它们是各轮单次采样范围，不是峰值曲线。所有轮的 dropped iterations、HTTP 500 和 HTTP 超时均为 0；业务 409 已分类为售罄或重复，不计为系统错误。

## 局限与下一步

每轮仅 5 秒、一次独立 3 秒预热，测试顺序固定且在同一开发机；无多机资源隔离。最高计划到达率 100/s 没有逼近系统最大吞吐，不能据此宣称容量或高并发性能提升。采样不连续、未观测到显著连接池排队或可单独归因的死锁；未测 40 连接。B0 与 B1 的短时波动说明结果只适用于当前环境，B1=B0 是保守决策。

建议先提交审查后的源码以获得不可变版本，延长时长、交错重复并补齐连接池及锁等待追踪，再用同一业务与工作负载比较 Redis + Lua；本数据不足以证明 Redis 一定必要或带来收益。禁止以本地示例的模拟 `userId` 和未授权 API 作为生产环境的安全方案。
