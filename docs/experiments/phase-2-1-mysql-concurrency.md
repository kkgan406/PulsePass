# Phase 2.1 — MySQL 并发实验报告

## 目的和范围

在独立 `pulsepass_bench` 数据库比较不安全读改写（A）、条件更新（B）和行锁读取（C），先验证正确性，再观察短时负载。所有实验表与正式 `pulsepass` 表分开；不修改正式订单索引、库存约束或 Docker Volume。测试用户是数字标识，不是真实个人数据。每轮以 UUID `run_id` 隔离，`lab_order` 的 `(run_id,user_id)` 唯一键表示本实验内同一用户、同一活动最多一笔订单。

## 实际环境

- Windows 11，AMD Ryzen 7 5800H，8 核 16 线程，物理内存约 15.4 GiB。
- Java 21.0.13、Spring Boot 3.5.16、MySQL 8.4.13、k6 2.4.0；MySQL 使用同一 Docker 容器。
- 每种方案的实验事务显式设置 `REPEATABLE READ`；MySQL 默认值实际查询也是 `REPEATABLE-READ`，`innodb_lock_wait_timeout=50` 秒。
- k6 HTTP 入口运行在 Windows 主机、只监听 `127.0.0.1:18081`，仅 `benchmark` profile 可启用；启动时检查 profile、回环地址、JDBC URL 和数据库名。连接池明确为 10。Tomcat 线程数未显式配置，Spring Boot 3.5.16 配置元数据默认 max=200、min-spare=10；未做运行期线程池采样。
- MySQL 容器未设置独立 CPU 或内存限制（inspect 返回 0）；Docker 容器内存可用上限快照 7.463 GiB。测试后快照：容器 CPU 0.46%、内存 488.2 MiB；主机 CPU 一次快照 15.8%。这些不是压测峰值或各轮平均值。

## 三种方案与事务

各方案均先按 `run_id,user_id` 检查订单，再在同一个本地数据库事务内处理一张库存并插入订单；异常回滚。唯一索引兜底并发重复用户。A、B、C 使用相同实例、表结构、连接池、隔离级别、初始库存和请求生成方法：

- A：`SELECT available ...` → Java 判断 → `UPDATE lab_inventory SET available=? WHERE run_id=?` → `INSERT lab_order`。此代码只在 benchmark profile 和 opt-in 测试中，不能用于正式购票。
- B：`UPDATE lab_inventory SET available=available-1 WHERE run_id=? AND available>0`，检查影响行数，再插入订单；采用与正式 InventoryMapper 相同的条件更新模式，但没有直接调用正式 Mapper，因为表和数据库不同。
- C：`SELECT available ... FOR UPDATE`，持有行锁直到更新库存、插入订单并提交；售罄时回滚。

实验模型把每个 run 当作一个活动及一个票种，订单均为有效订单，没有建模取消订单、活动售票时间、用户认证或正式 API 的全部查询。因此只能比较隔离场景的数据库操作，不能将吞吐量直接当作正式购票系统性能。

## E1：确定性竞态

每轮库存 1，两个线程、两个独立 JDBC 连接和事务，均使用 `REPEATABLE READ`；每种方案各运行三次。A 在普通 SELECT 之后使用 10 秒超时屏障，让两个事务都读到库存 1 后继续；B/C 的启动屏障在请求更新或锁定读取前，C 不在持锁之后等待对方到屏障。提交前插入不同用户的订单。每轮最终行数通过独立连接核查。

| 方案 | 每轮初始库存 | 第 1 / 2 / 3 轮成功订单 | 每轮最终库存 | 超卖 |
| --- | ---: | --- | ---: | --- |
| A | 1 | 2 / 2 / 2 | 0 | 每轮 1；旧值覆盖产生丢失更新 |
| B | 1 | 1 / 1 / 1 | 0 | 无 |
| C | 1 | 1 / 1 / 1 | 0 | 无 |

E1 实际进程日志为 `E1 scheme=A round=1 initial=1 stock=0 orders=2 successes=2 oversold=1` 等；运行后只按本轮 UUID 删除测试行。

## 锁竞争、错误与限制

增加 VU 后，distinct 的 B 从 1 VU 的 104.3 RPS、P95 11.8 ms，变为 100 VU 的 226.2 RPS、P95 501.5 ms；C 为 205.8 RPS、P95 538.2 ms。响应延迟显著上升而吞吐增长有限，现象与热点行串行化和有限连接池一致，但未采集各轮连接池等待或锁等待时间，不能将比例归因于某个瓶颈。

测试后 MySQL `Innodb_row_lock_waits=10300`、`Innodb_row_lock_time=383707 ms`、当前 `performance_schema.data_lock_waits=0`；它们是容器启动以来的累计值或测试后瞬时值，包含其他操作，无法归因到本次实验或某一方案。本次未观察到 HTTP 500、死锁或锁等待超时，也没有相应典型错误日志；没有采集负载期 MySQL CPU 曲线。

A 的 E1 超卖和 E2 库存差额是实际结果；B/C 在本次实验中的库存差额与重复有效订单数为零，但有限测试不证明不存在所有并发问题。E2 的 A 没有额外强制屏障；隔离表仅模拟一活动一票种。24 轮每轮仅 5 秒，机器其他进程、JIT 和顺序效应未控制。原始 JSON/日志默认被 Git 忽略；补充售罄实验曾覆盖 distinct/50/B 的同名原始 JSON，该主表行的汇总 CSV 已保留，但原始 JSON 不可恢复。脚本现已把库存与时长加入文件名，避免再次覆盖。
