# 第一版业务规则与不变量

同一 User 对同一 Activity 最多拥有一笔有效 Order：PENDING、CONFIRMED 有效，CANCELLED 不计入。例如购买活动 A 的 VIP 后不能再购买 A 的 Regular，但可以购买活动 B。采用活动级规则是为了简化业务模型、聚焦高并发与一致性、便于演示重复订单问题，并避免扩大票务规则复杂度。参见 [ADR-0001](../adr/0001-one-order-per-user-per-activity.md)。

Activity 只有在存在、状态为 ON_SALE 且当前时间满足 saleStartTime <= now <= saleEndTime 时可售；不可仅依据时间判断。TicketType 必须为 ENABLED 才可购买。有效订单的可售条件指创建时的条件，不要求活动结束或取消后历史订单仍处于可售活动之下。

下表的主要检查层指未来基础实现的业务逻辑层；目前尚无实现。第二道保护仅为未来可能性，并非已选技术方案，也不替代业务检查或保证并发安全。

| 不变量及含义 | 破坏后的业务后果 | 当前设计的主要检查层 | 未来第二道保护可能性 |
| --- | --- | --- | --- |
| TicketType 必须属于对应 Activity：购票所选票种归属所选活动。 | 购买了错误活动的票。 | 业务逻辑层检查归属。 | DB 关联约束等可辅助保护。 |
| Inventory 必须对应有效 TicketType：库存归属存在的票种。 | 库存成为孤立资源或扣减错误资源。 | 业务逻辑层检查票种及库存归属。 | DB 引用约束等可辅助保护。 |
| availableStock >= 0：可用库存不能为负。 | 超卖或库存记录失真。 | 业务逻辑层检查及扣减。 | DB 约束或未来 Redis 保护可能辅助；并发语义需另行设计。 |
| availableStock <= totalStock：可用量不超过总量。 | 可售配额超过设定总量。 | 业务逻辑层检查库存变更。 | DB 约束等可能辅助保护。 |
| 同一 User 对同一 Activity 最多一笔有效订单。 | 同一活动被重复购买。 | 业务逻辑层查询有效订单并检查。 | DB 或未来 Redis 保护可能辅助；状态和并发语义需另行设计。 |
| 只有可售 Activity 可以产生有效订单：创建时状态及时间均满足售票条件。 | 在暂停、取消或售票期外产生订单。 | 业务逻辑层检查状态和时间。 | DB 等保护可研究；动态时间及并发状态变化需另行设计。 |
| 只有 ENABLED TicketType 可以购买。 | 已停用票种仍被售出。 | 业务逻辑层检查票种状态。 | DB 等保护可研究；并发状态变化需另行设计。 |
| 每笔第一版订单 quantity = 1。 | 订单数量不符合限购和库存计算假设。 | 业务逻辑层固定并检查数量。 | DB 约束等可能辅助保护。 |
| Order.activityId 必须等于其 TicketType.activityId。 | 订单归属与所购票种不一致，限购判断失真。 | 业务逻辑层检查票种归属并记录活动。 | DB 关联约束等可研究作为辅助保护。 |

以上检查不天然解决并发竞态或库存与订单之间的一致性问题。取消订单是否恢复库存、状态转换以及有效订单创建后的活动状态变化处理，留待后续明确。
