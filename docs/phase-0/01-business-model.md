# 业务模型

## 背景与范围

活动组织者提供活动和不同票种，用户选择票种并提交购买请求。Phase 0 只描述基础同步购票所需的业务概念、流程及未来风险，不定义最终存储方案或实现业务代码。第一版每次购买一张票；同一用户对同一活动最多拥有一笔有效订单（PENDING 或 CONFIRMED），CANCELLED 不计入。

## 核心对象

- **User**：购票主体，以身份标识关联其订单。
- **Activity**：描述活动及其售票时间、活动时间和售票状态，作为票种的归属。
- **TicketType**：描述某活动下可购买的票种及价格，归属于一个 Activity。
- **Inventory**：描述一个 TicketType 对应的总库存与可用库存，是可被消耗的资源。
- **Order**：记录用户购买具体票种的交易事实，包括数量、金额、状态和创建时间。

## 职责边界

Activity 和 TicketType 分开，是因为一个活动可以提供多个名称、价格不同的票种，而活动时间和状态由活动统一描述。每个 TicketType 有独立库存，避免一个票种的销售消耗或混淆其他票种的配额。

Inventory 单独作为业务概念，用于表达资源总量和可用量及其变化；它不是订单。Order 则记录谁购买了什么、数量和金额，保留交易发生时的事实；它不是库存余额。库存变化与订单记录之间的一致性是未来需要解决的问题。

## 暂不考虑

支付、退款、座位选择、优惠券、会员、推荐系统、OAuth 和微服务均不在当前范围。
